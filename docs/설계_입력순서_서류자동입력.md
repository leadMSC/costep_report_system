## 사용자 결정으로 원문과 달라진 점 (우선 적용)
1. **대표자 민감정보(NICE·KCB 신용점수, 주택 형태)는 1단계 대표자에서 함께** 받습니다. 원문 권장(5단계)과 다름. 단, 「개인신용정보 입력 동의」 체크 후에만 펼칩니다.
2. **보고서 분야는 고객 열기 때 상담목적 칩**으로 고릅니다(규모별 6종과 1:1, 최대 2개) → 7단계에서 발행 분야 확정.
3. 초대 없는 1인 컨설턴트: **가입 신청서 → 운영자 승인**(원문 F-1 권장과 같음).
4. 1차 범위: **프로필(0단계) → 고객사 정보 입력(단계형)**. 서류 자동입력은 2차.
5. 완결성 비판 반영: 규모는 2단계에서 소상공인 여부만, 소·중 구분은 4단계 매출 뒤 / 서식1은 「분야 × 서식」 준비도로 판정(2단계 직후 출력 가능 아님) / 서식1 시행일 = 발행일 / 업종 선택칸은 상태(현재)·계획(미래) 두 값으로 분리 / 주민번호 필터는 라벨 기준(법인등록번호 보존) / 발행 WP(WP-P)·개인정보 고지 WP(WP-03b) 추가 / 같은 PC 계정 분리·승인 대기자 RLS는 2026-10-13 운영 반영 때 수정 완료(L-053).

# Ⅰ. 최종 설계 (합성안 원문)

# 경영진단 리포트 생성기: 입력 순서 재설계, 서류 자동입력, 개발 과업 최종안

## A. 결론 요약

1. **기준안과 접목:** 기준은 '원칙 충실안'입니다. 사용자 원칙을 가장 잘 지키고 빠진 칸이 가장 적기 때문입니다. 여기에 면담 흐름안의 세 가지(단계 공통 틀, 민감 정보 뒤로 미루기, 기본값 정리 우선)와 서류 먼저안의 세 가지(자료 투입 패널, 확인표, 다른 회사 서류 차단)를 붙였습니다.
2. **입력 순서:** 0 작성자(펌·컨설턴트) → 고객 열기(식별값만) → 1 대표자 → 2 사업자(끝에서 업종·규모 확정) → 3 사업 운영 → 4 실적·비용 → 5 부채·의무·신용 → 6 미래 계획·사업계획 → 7 점검·발행.
   - 0단계 값은 계정과 펌에 저장되어 다음 로그인 때 자동으로 불러옵니다.
   - 각 단계 안은 「확인(불변) → 과거 → 현재 → 미래」 순서로 묻습니다.
3. **기존 칸 처리:** 기존 칸 93개와 대출표 6열을 하나도 빼지 않고 모두 배정했습니다.
   - 입력칸이 없어지는 것은 3개입니다. 작성자 칸은 계정으로 옮기고, 고금리 체크는 자동 판정으로, 월 이자는 읽기 전용으로 바꿉니다.
   - 나머지는 흡수하거나 형식만 바꿉니다.
   - 새 칸은 1차에 약 25개만 넣습니다. 대부분 칩 버튼과 숫자 칸입니다.
4. **서류 자동입력:** 서류 32종을 우선순위 1(8종) / 2(15종) / 3(9종)으로 나눴습니다.
   - 브라우저 안에서 텍스트 PDF → 엑셀 → OCR 순서로 읽습니다.
   - 확인표에서 사람이 승인한 값만 칸에 채웁니다. 원본 파일은 저장하지 않습니다.
5. **개발 묶음:** 과업 묶음(WP) 22개와 상시 회귀 검증을 세 번에 나눠 출시합니다.
   - 1차: 순서·계정·저장. 서류 없이도 새 흐름으로 끝까지 작성할 수 있게 합니다.
   - 2차: 서류 자동입력(홈택스 PDF·등기·엑셀·은행 서류)
   - 3차: 인증·인력 서류, OCR, 면담 모드
   - 가장 먼저 할 일: 목업 확인(WP-00), 그리고 기본값이 사실처럼 출력되는 결함 정리(WP-01)

**드러내 놓고 정한 원칙 예외 3가지**
1. **상호·사업자번호를 「고객 열기」에서 먼저 받습니다.** 중복 고객 차단, 서류가 같은 회사 것인지 대조, 문서번호의 열쇠이기 때문입니다. 2단계에서는 확인만 합니다.
2. **진단일·회차·협약명·작성자·상담 목적은 진단 건 머리 바에 둡니다.** 고객 정보가 아니라 이번 진단에 대한 정보라서 순서 원칙의 대상이 아닙니다. 상담 목적은 칩으로 한 줄만 받고, 상세 계획은 6단계에서 받습니다.
3. **대표자 신용점수와 주택 형태는 5단계 「대표자 개인 신용」 구획에서 받습니다.** 가장 자주 바뀌고 가장 민감한 정보라서, 큰 흐름(불변 → 가변)과 면담 흐름 양쪽에 맞습니다. 결정 질문 F-2에서 확인을 받습니다.

**모든 단계에 같은 틀을 씁니다.**
- 구획 순서는 「A 확인 → 과거 → 현재 → 미래」입니다.
  - A 확인: 불변 정보입니다. 서류값이나 지난 진단 값을 보여주고 「모두 맞음」 한 번으로 확인합니다.
  - 현재 구획 머리에는 기준일을 한 번 표시합니다.
  - 내용이 없는 구획은 숨깁니다.
- 구획 제목은 시점(과거/현재/미래)으로만 붙입니다. 변동성(불변/준불변/가변)은 칸 옆 작은 배지로 표시합니다.
- 칸마다 「모름 / 해당 없음 / 나중에」 버튼을 둡니다. 셋 다 빈칸과 따로 저장하고, 「나중에」를 누른 칸은 7단계의 추후 요청 목록으로 모입니다.
- 진행을 막는 곳은 세 군데뿐입니다.
  - 0단계: 내 이름(처음 한 번)
  - 고객 열기: 상호
  - 2단계에서 3단계로 넘어갈 때: 업종·규모 확정
- 나머지 필수 칸은 출력 직전에만 막습니다.
- 입력 순서와 출력 순서는 따로 둡니다. 서식2와 서식4는 지금 양식 순서를 그대로 유지합니다.

**표기**
- 시점: 과 = 과거, 현 = 현재, 미 = 미래
- 변동: 불 = 불변, 준 = 준불변(해마다 바뀜), 가 = 가변(방문마다 바뀜)
- 필수
  - 진행: 비면 다음 단계로 못 넘어감
  - S1·S2·S4: 비면 해당 서식 출력을 막음
  - 권장 / 선택 / 자동(계산값)
- 저장: 펌 / 계정 / 고객 / 진단 건
- 릴리스: 바뀌는 시점(1차 / 2차 / 3차). 「–」는 위치 이동만 함
- **NEW** = 새 칸

- 라벨은 일반 양식 기준(◐)입니다. U0 샘플로 정규식을 확정합니다.

### D-3. 추출 방식 단계

**모든 서류의 공통 흐름**

1. **받기:** 드롭존 또는 [파일 찾기]로 여러 파일을 받습니다. 최대 30개, 파일당 20MB입니다. 파일은 메모리에서만 처리합니다.
2. **형식 판별:** 확장자가 아니라 파일 앞부분 글자로 판별합니다.

   | 파일 앞부분 | 판별 결과 |
   |---|---|
   | `%PDF` | PDF |
   | `PK` | xlsx 또는 hwpx(내부 목록으로 구분) |
   | `D0 CF 11 E0` | xls 또는 hwp. hwp면 "PDF로 저장해 올려 주세요" 안내 |
   | `<html` 또는 `<table` | 확장자는 .xls인데 실제로는 HTML 표인 파일 |
   | `FF D8` / `89 50` | JPG / PNG |
   | 일반 글자 | CSV. UTF-8로 읽다 실패하면 EUC-KR로 다시 읽음 |
3. **문서 종류 판별:** 제목 키워드 1개 + 필수 라벨 2개 이상이 맞아야 판정합니다. 한 PDF에 여러 서류가 섞이면 쪽마다 판별합니다. 실패하면 사용자가 드롭다운에서 고릅니다.
4. **글자 꺼내기:** 아래 세 경로 중 하나로 꺼냅니다.
5. **개인정보 필터:** 저장하기 전에 주민번호 패턴을 가립니다(D-5).
6. **라벨 사전으로 값 추출:** `doc_registry.json`에 문서 종류마다 판별 키워드, 라벨, 정규식, 단위, 대상 칸을 적어 둡니다.
7. **정규화:** 금액(쉼표, △, 괄호 음수), 날짜 형식, 단위 환산(칸 사전의 단위로)을 맞춥니다.
8. **검증:** 검증번호, 같은 회사인지(다르면 차단), 대차 검산, D06과 D08 교차 확인, 서류 유효기간을 봅니다.
9. **확인표 → 적용:** `applyFieldPatch(patch, source)`로 칸만 채웁니다. 지금의 `applyFormData`는 규모·업종을 초기화하므로 쓰지 않습니다. 출처는 `form_data.sources`에 기록합니다.

**글자를 꺼내는 세 경로** (출시 순서: 텍스트 PDF → 엑셀 → OCR)

| 경로 | 대상 | 방식 | 출시 |
|---|---|---|---|
| ① 텍스트 PDF | D01·D03·D06·D08·D17·D22·D23 등 | pdf.js를 정확한 버전으로 고정하고, 서류를 처음 올릴 때만 불러옴. 한글 글자표(cMap) 설정이 필수. 글자 조각을 좌표 기준으로 줄로 다시 묶고, 라벨의 오른쪽이나 바로 아래 칸 값을 집음. 라벨은 공백을 지우고 비교 | 2차 |
| ② 엑셀·CSV | D11·D12·D13 | SheetJS 공식 CDN 0.20.x를 버전 고정. npm에 남아 있는 `xlsx` 0.18.5는 알려진 취약점 때문에 쓰지 않음. 머리글 행은 키워드로 찾음 | 2차 |
| ③ OCR | D02·D16·D20·D31, 그리고 글자가 없거나 깨진 PDF | tesseract.js 한글 모델을 브라우저에서 실행. 회색조·이진화·기울기 보정을 거침. **자동 적용 0건**(모두 한 칸씩 확인) | 3차 |

- 텍스트 PDF에서 깨진 글자 비율이 높거나 글자가 없으면 ③ OCR로 넘깁니다(3차 이전에는 "직접 입력" 안내).
- 클라우드 OCR과 AI 추출은 비용과 개인정보 승인 전까지 쓰지 않습니다(계획서 B-5).
- 오프라인이거나 라이브러리를 불러오지 못하면 "직접 입력"으로 안내합니다. 한 파일·오프라인 동작 원칙을 지킵니다.

### D-4. 확인 화면 규칙

- **열:** 단계 / 앱 항목 / 지금 값 / 서류 값(정규화한 값) / 원문 위치(서류·쪽·라벨·원문 조각, 누르면 미리보기 강조) / 신뢰도 / 처리(적용 · 유지 · 직접 수정)
- **신뢰도**

  | 등급 | 조건 |
  |---|---|
  | 높음 | 텍스트 PDF + 라벨 정확히 일치 + 검증 통과 |
  | 중간 | 라벨이 비슷하게만 일치, 검산할 수 없음, 0원·말소 의심 |
  | 낮음 | OCR 값, 또는 검산 실패 |

- **기본 동작**
  - 빈 칸은 '적용'이 미리 체크됩니다.
  - 이미 값이 있는 칸은 '유지'가 기본이고 차이를 강조합니다.
  - 직접 입력한 값은 덮어쓰지 않습니다.
- **일괄 확인:** 「모두 적용」 「이 단계 서류값 모두 확인」은 신뢰 '높음'만 처리합니다. '중간'과 '낮음'은 한 칸씩 확인해야 합니다.
- **서류끼리 값이 다를 때**
  - 기본 순서: 국세청·등기소 발급 > 기관 확인서 > 세무대리인 결산서 > 회사 자료 > OCR
  - 매출·잔액·인원처럼 변하는 값은 발급일이 최근인 서류를 씁니다.
  - 번호·성립일처럼 불변 값이 다르면 자동으로 고르지 않고 경고합니다.
- **되돌리기:** 서류 단위로 되돌릴 수 있습니다. 적용한 칸에는 출처 배지가 붙습니다.
- **출력 전 점검:** 확인 전 서류값과 만료된 서류를 7단계에 모아 보여줍니다.
- **서류 상태:** 미제출 / 추출 완료 / 확인 필요 / 유효기간 만료 4가지입니다.

### D-5. 개인정보 처리 원칙

1. **주민등록번호:** 모든 추출 경로 앞에 공통 필터를 둡니다. `\d{6}-?[1-8]\d{6}` 패턴을 찾으면 메모리에서 바로 가리고 생년월일만 계산합니다. `form_data`, 로그, `audit_logs.detail`, 오류 보고 어디에도 남기지 않습니다.
2. **명단 서류**(4대보험 명부, 주주명부, 등기 임원): 인원수와 관계·지분만 남깁니다. 대표가 아닌 사람의 이름, 임대인 정보는 저장하지 않습니다.
3. **계좌번호:** 은행명과 끝 4자리만 남깁니다.
4. **대표자 신용정보**(신용점수, 연체, 주택): 5단계 동의 체크와 동의 일시를 기록한 뒤에만 저장합니다. 동의 전에 올라온 D18·D20 값은 메모리에만 두었다가 버립니다. 동의 요건은 법률 검토가 필요합니다.
5. **원본 파일:** 기본은 보관하지 않습니다. 브라우저에서 읽고 바로 버리며 서버로 보내지 않습니다. 보관 옵션(펌 관리자가 켜는 Storage 비공개 저장, 기간 만료 자동 삭제, 감사 로그)은 3차 선택 과업입니다.

## F. 결정이 필요한 질문

1. **펌 정보는 누가 고치나, 처음 가입한 사람은 어떻게 시작하나?**
   - 권장: 펌 정보는 펌 단위로 저장하고 펌 관리자만 고칩니다.
   - 초대 없이 가입한 사람은 가입 신청서에 희망 펌 이름·로고와 내 정보를 적습니다. 운영자가 승인하면 1인 펌(본인이 관리자)이 만들어지거나 기존 펌에 합류합니다.
   - 이름·직함·연락처는 계정별로 저장합니다.
2. **대표자 신용점수와 주택 형태를 어디서 묻나?**
   - 권장: 5단계 「대표자 개인 신용」 구획에서, 동의를 받은 뒤 묻습니다. 신용점수는 모든 규모에 보여주되 선택 칸으로 둡니다.
   - 1단계 대표자에는 변하지 않는 인적사항과 경력만 둡니다.
3. **고객과 진단 건의 데이터 경계, 펌 안 공개 범위는?**
   - 권장: 1차에 `clients.profile` 마이그레이션을 포함합니다. 재진단 때 고객 정보를 자동으로 이어 쓰는 것이 핵심 요구이기 때문입니다.
   - 고객 목록은 펌 전체가 공유하되 기본 필터는 「내 고객」으로 둡니다.
   - 신용 정보를 작성자와 펌 관리자만 보게 하는 제한은 3차(WP-21)에서 합니다.
4. **새 칸을 1차에 어디까지 넣나?**
   - 권장: 출력 오류를 고치거나 판정 근거가 되는 약 25칸만 1차에 넣습니다(WP-07, 칩·숫자 위주).

5. **서류는 어떻게 처리하나?**

## (2) 불변→가변, 과거→현재→미래 순서 위반

**2-1. 업종 선택칸 하나를 현재 구획과 미래 구획 두 곳에 보여줍니다(B-5 #12).**
- 값 하나에 「미보유」와 「취득 희망」이 함께 들어 있습니다. 예: `mfg_direct` 'need' = "미보유 (조달청 진입 희망)".
- 현재 구획에서 '미보유'를 고르면 미래 의향이 사라집니다. 미래 구획에서 고르면 현재 상태를 미래 구획에서 묻는 셈이 됩니다.
- 수정안
  - 상태(보유 / 미보유 / 미확인, 현재)와 계획(희망 / 불필요 / 미정, 미래)의 두 값으로 나눕니다.
  - 옛 값 변환: yes → 보유, need → 미보유 + 희망.
  - `INDUSTRY_GAPS`는 '미보유'로 판정하고, '희망'이면 문장에 덧붙입니다.

**2-2. 스마트주문 통합 칸(`smb_chk_smartorder` + `food_order`)이 미래 구획에 있습니다(B-5 #14).**
- 「보유」 상태를 미래 구획에서 묻게 됩니다.
- 수정안: 현재 구획에 「보유 여부」, 미래 구획에 「도입 희망」으로 나눕니다.

**2-3. 2단계 현재 구획 안에서 가변 정보가 준불변 정보보다 먼저 나옵니다.**
- 인원·근로계약·4대보험(가변) 뒤에 지분·자본금·확인서(준불변)가 옵니다.
- 수정 순서: 과세유형 → 소재지 → 지분·자본금 → 점유·면적·보증금 → 확인서 → 인원 → 근로계약·4대보험 → 진단 틀 확정

**2-4. 1단계 `ceo_flags`(여성 / 장애인 / 재창업)를 '현재' 구획에 두었습니다.**
- 여성·장애인은 불변 정보이므로 A 확인 구획으로 옮깁니다.
- 재창업은 `ceo_prev_biz`(과거)와 중복입니다. 그 값에서 자동 계산하고 칸은 없앱니다.
- 공동대표 위치가 문서 안에서 다릅니다. B-0 표는 '현재', B-3 표는 'A 확인'입니다. 하나로 통일합니다.

**2-5. 4단계의 월 이자(`smb_cost_interest`)가 5단계 대출표에서 계산됩니다.**
- 그래서 4단계에 보이는 고정비 합계·손익분기와 WP-19 중간 결과 카드는 5단계 전까지 이자가 빠진 값입니다.
- 수정안
  - 4단계에 "이자: 5단계 입력 후 반영(현재 미반영)"을 표시합니다.
  - 손익분기 판정 문장과 중간 카드는 5단계를 마친 뒤에만 보여줍니다.

**2-6. 선언된 예외 3개와 상담 목적 칩을 맨 앞에서 묻는 것은 문제없습니다.**
- 다만 상담 목적이 보고서 종류와 연결되어야(1-1) 맨 앞에서 묻는 의미가 생깁니다.

## (3) 출력에 필요한 입력이 출력보다 늦게 나오는 곳

**3-1. 「2단계 후 서식1 출력 가능」이 틀립니다(B-4 하단, C-2 목업 「2 후: 서식1·3」).**
- 소상공인 경영개선 서식1 본문(2342행)에 [SMB_FIXED_TOTAL]이 들어 있습니다.
- 이 값을 채우려면 4단계 고정비와 5단계 이자가 필요합니다.
- 2단계에서 출력하면 "월 고정 지출 총액 0만원 반영"이 고객 공문에 그대로 나갑니다.
- 또 서식1 본문은 보고서 종류마다 다른데, 그 선택이 흐름에 없습니다.
- 수정안: 둘 중 하나로 합니다.
  - 준비도를 「분야 × 서식」으로 계산하고, 이 경우 서식1은 5단계 이후에 출력 가능으로 표시합니다.
  - 서식1 본문에서 숫자 치환자를 빼고 "붙임 결과보고서 참조"로 바꿉니다.
- 서식3은 규모·업종만 쓰므로 2단계 후 출력이 맞습니다. 단, 3차에 「향후 12개월 일정」이 붙으면 5단계 이후로 바뀝니다.

**3-2. 2단계 관문에서 규모를 끝까지 확정하게 되어 있습니다.**
- 소기업과 중기업은 인원이 아니라 평균매출액(4단계)으로만 갈립니다. 2단계에서는 근거 없이 고르게 됩니다.
- 수정안
  - 2단계에서 3단계로 넘어가는 관문에서는 「소상공인 vs 소·중기업」만 확정합니다. 4단계 화면이 이 둘로만 갈리기 때문입니다.
  - 소기업과 중기업은 4단계에서 3개년 매출을 넣은 직후 자동 추천하고 사람이 확인합니다.
- 버튼 설명 정정 내용
  - 소상공인: 5인 미만. 제조·건설·운수·광업은 10인 미만.
  - 중기업: 인원이 아니라 매출 기준입니다.

**3-3. 서식1 시행일을 진단일(방문일)로 두었습니다.**
- 공문의 시행일은 발행일입니다. 방문일과 발행일이 다르면 사실과 다른 날짜가 찍힙니다.
- 수정안: 시행일은 발행 시점(`documents.issued_at`)으로 하고, 진단일은 서식2 머리에 따로 넣습니다.

**3-4. 다른 컨설턴트가 연 진단 건에서는 원래 작성자의 연락처를 읽을 수 없습니다.**
- RLS(`profiles_read_self`)는 본인과 관리자만 프로필을 읽게 합니다.
- 수정안
  - 진단 건을 만들 때 `author_label`과 함께 `author_contact`(전화·메일)를 스냅숏으로 저장하고, 발행 때 고정합니다.
  - `co_consultants` 선택용으로, 같은 펌 구성원의 이름·직함만 보여주는 함수나 뷰를 WP-03에 추가합니다.

**3-5. 「6단계에서 연계 공고 우선순위 결정」은 1차에서 실제로 되지 않습니다.**

- 수정안: 이 내용을 WP-20(3차) 범위로 표시합니다.

**3-6. 사업계획 자동 생성기의 근거 없는 문구가 WP-01 제거 대상보다 더 많습니다(3311~3436행).**

  - '주요 수요처 및 대형 바이어', '원자재 전문 공급처', '안정적 사업 인프라 보유', '견실한 결산 매출 기반'

## (4) 서류 자동입력 매핑 오류와 비현실적인 부분

**4-1. 주민번호 필터가 법인등록번호를 지웁니다.**
- `\d{6}-?[1-8]\d{6}` 패턴은 법인등록번호(예: 110111-1234567)도 잡습니다.
- D01·D03에서 `corp_reg_no`를 채우기 전에 값이 가려집니다.
- 수정안: 라벨 기준으로 판정합니다.
  - '법인등록번호' 라벨 옆 값이 법인번호 검증을 통과하면 가리지 않습니다.
  - '주민(등록)번호'·'생년월일' 라벨 옆 값과 라벨 없는 패턴만 가립니다.

**4-2. D01을 「공개본만」 받으면 전체 주민번호를 일부러 받게 됩니다.**
- 비공개본에도 앞 6자리는 보입니다.
- 수정안
  - 비공개본을 기본으로 안내합니다.
  - 태어난 세기는 나이 범위(만 15~100세)로 추정한 뒤 사람이 확인합니다.
  - D03도 뒷자리가 가려져 있으므로 같은 방식으로 처리합니다.

**4-3. 서류 없이도 사업자번호 가운데 2자리로 사업자 구분을 제안할 수 있습니다.**
- 가운데 2자리의 뜻

  | 자리 | 구분 |
  |---|---|
  | 01~79 | 개인 과세 |
  | 90~99 | 개인 면세 |
  | 81·86·87·88 | 영리법인 본점 |
  | 85 | 영리법인 지점 |
  | 82 | 비영리법인 |
  | 80·89 | 비법인 단체 |

- 수정안: 「고객 열기」에서 번호를 넣는 즉시 `corp_form`과 면세 여부를 제안합니다.
- 검증번호 설명도 보완합니다. 가중치 합에 「9번째 자리 × 5」의 십의 자리를 더해야 합니다.

**4-4. D08의 「최근 2기 합 ÷ 12」가 맞지 않는 경우가 있습니다.**
- 법인은 예정신고와 확정신고가 따로 찍힙니다.
- 간이과세자는 1년이 과세기간 1기입니다(2021년 7월 이후).
- 수정안
  - 각 행의 과세기간 시작일·종료일을 읽어 최근 12개월에 해당하는 행만 더합니다. 수정신고가 있으면 최신 행을 씁니다.
  - 더한 값을 개월 수로 나눕니다.
  - 과세와 면세를 함께 하는 사업자는 면세 수입금액을 따로 더합니다.

**4-5. 개인 소상공인 대부분은 D06(표준재무제표증명)이 없습니다.**
- 간편장부대상자에게는 표준재무상태표가 없습니다.
- 수정안
  - 개인은 D08·D09를 우선합니다.
  - 확인표에 발급 가능 시점(법인 3월 말, 개인 5월 말 신고 후)을 표시합니다.

**4-6. D11(전자세금계산서 엑셀) 처리에 네 가지를 보완해야 합니다.**
- 공급받는자가 개인 소비자면 등록번호가 주민번호입니다. 이 값을 묶음 기준으로 쓰지 말고, 가린 값으로 「개인 고객」 한 묶음으로 처리합니다.
- 상대방 대표자명·이메일 열은 버립니다.
- 조회 기간 제한으로 12개월 자료가 여러 파일일 수 있습니다. 여러 파일을 합치고 승인번호로 중복을 지웁니다.
- D08과 비교하는 경고는 손님에게 직접 파는(B2C) 업종에서 늘 뜹니다. 비교 대상을 D10의 「세금계산서 발급분」으로 바꿉니다.

**4-7. D17은 은행에 따라 금리·상환방법이 안 나옵니다(샘플로 확인 필요).**
- 수정안
  - 금리가 없으면 D18처럼 「보완 필요」로 표시합니다.
  - 예금 계좌번호는 추출 대상이 아니므로 즉시 가립니다.

**4-8. D18(크레딧포유)은 대표자 개인의 신용정보입니다.**
- 법인 대출은 나오지 않습니다. 개인사업자는 주택담보대출·카드론 같은 가계대출이 섞여 나옵니다.
- 수정안
  - 개인사업자는 「개인사업자대출」 행만 대출표 초안으로 만듭니다.
  - 나머지는 대표 가계부채로 따로 둡니다. 민감 정보이므로 동의 후에만 받고, 대출표에는 넣지 않습니다.
  - 법인은 D18을 대출표에 넣지 않습니다.

**4-9. D22·D23(납세증명서)의 대조 기준이 개인사업자에게 맞지 않을 수 있습니다.**
- 개인사업자의 납세증명서는 대표 개인 명의일 수 있어서, 「사업자번호가 다르면 차단」 규칙이 맞지 않습니다.
- 수정안: 개인은 대표자 성명 + 생년월일로 대조하고, 법인은 법인번호·사업자번호로 대조합니다.

**4-10. 인원 매핑 두 곳이 비현실적입니다.**
- D05 확인서에는 보통 상시근로자 수가 없습니다. 샘플로 확인한 뒤 매핑을 지웁니다.
- D14의 가입자 수는 상시근로자 수와 다릅니다(대표자·단시간·일용 근로자 차이). 후보값으로만 씁니다.

- 반기납부 사업자는 6개월 단위로 신고하므로 「최근 3개월 평균」이 성립하지 않습니다.
- 총합계(A99)에는 퇴직·사업소득이 섞여 있습니다.
- 수정안
  - 근로소득 간이세액(A01)과 일용근로(A03)의 지급액만 쓰고, 귀속 개월 수로 나눕니다.
  - A01 인원은 `sme_employees` 후보로 씁니다. 이렇게 하면 B-4 #16과도 맞습니다.

**4-12. 서류 두 종의 매핑이 비어 있습니다.**

## 핵심 발견

1. **회사 정보 대부분이 S2에서만 쓰입니다.** S3는 회사 입력을 전혀 쓰지 않고, S1은 상호·사업자구분·사업자번호·컨설턴트만 씁니다. 지원사업 매칭(S3 연계 박스와 RADAR)도 규모·업종 버튼 두 개로만 결정됩니다.

2. **'빈칸'이 없는 칸들이 기본값을 사실처럼 출력합니다.**
   - 사업자구분 법인, 주택 자가, 원자재 '현저히 상승' + 판매단가 '동결', 고금리 차입 체크, 근로계약 '미비'
   - 업종 칸의 견본 문구(「공인 전문인력 6명」 「직영차량 12대」 등)
   - 모든 select·체크 칸에 **'미확인' 상태가 필요합니다.**

3. **사업계획 생성기가 사실을 꾸밉니다.** 인증 칸이 비어 있으면 「ISO9001」 「벤처기업 인증」을 보유한 것처럼 쓰고, 「수상 경력」 같은 근거 없는 역량 문구와 업종별 고정 예산을 넣습니다.

4. **같은 정보를 두 곳에서 받아 서로 어긋날 수 있습니다.**
   - 고금리: 체크박스 smb_chk_cardloan ↔ 차입금 표의 금리
   - 월이자: smb_cost_interest ↔ 차입금 표 합계(자동으로 덮어씀)
   - 부채: 부채총계 ↔ 차입금 표 합계
   - 인증: corp_certs ↔ it_cert, esg_cert, service_cert, food_haccp
   - 특허: corp_patents ↔ bio_patent, content_ip
   - 판매채널: corp_sales_channel ↔ dist_chan
   - 스마트주문: smb_chk_smartorder ↔ food_order
   - 체납: 체크박스 ↔ smb 「금융비용」 서식의 고정 문구 「완납 확인」

5. **받기만 하고 거의 쓰지 않는 칸이 있습니다.**
   - corp_vendors: S2에만 나오고, BP는 읽기만 함
   - 3개년 재무 중 2023·2024의 영업이익·부채·자본: 표시만 함
   - NICE·KCB 점수: 표시만 함
   - smb_area_pyung: 라벨은 철거지원금 산정용인데 계산에 안 씀
   - 소상공인일 때 업종 칸 대부분

6. **단위와 형식이 들쭉날쭉합니다.**
   - 소상공인 지출과 차입금 표는 만원, 소기업·중기업 재무는 백만원, 사업계획 예산은 억·만원 자유 문장
   - 생년월일은 text, 설립일은 date
   - 3개년 재무 id는 연도 고정인데 라벨은 상대 표시(Y-3/Y-2)
   - 상환방법과 만기가 한 칸
   - 월평균 매출은 기간 기준 없음
   - 서류 자동입력을 붙이려면 **회계연도 키와 단위 정규화가 먼저** 필요합니다.

7. **여러 사람이 쓰기에는 구조가 부족합니다.**
   - 펌 정보는 계정별로 이미 저장됩니다.
   - 하지만 컨설턴트 이름은 고객 자료 안에 저장되고, 프로필에서는 칸이 비었을 때만 채웁니다.
   - 고객 목록은 그 PC 브라우저(localStorage)에만 있어 계정별로 나뉘지 않습니다.
   - Supabase에 `clients`, `assessments`, `doc_sequences` 테이블은 만들어져 있지만 앱이 쓰지 않습니다.

8. **시점 축이 비어 있습니다.**
   - 거의 모든 칸이 '현재'입니다.
   - 과거 축은 소기업·중기업 3개년 재무뿐이고, 소상공인은 매출·종업원 추이가 없습니다.
   - 미래 축은 사업계획 자유 문장뿐이라 숫자로 된 목표가 없습니다.
   - 요구하신 '불변→가변, 과거→현재→미래' 순서로 다시 배치하려면 위 「없는 필드」를 보강해야 합니다.

9. **현재 입력 화면 순서는 변동성 순서와 맞지 않습니다.**
   - 지금 순서: 규모·업종 → (사업자 + 대표자 + 컨설턴트가 한 카드에 섞임) → 거래처 → 차입금 → 소상공인/재무 → 업종 → 사업계획
   - 컨설턴트 칸이 고객 카드 안에 있습니다.
   - 대표자의 불변 정보(생년월일)와 가변 정보(주택 소유형태, 신용점수)가 서로 다른 카드에 흩어져 있습니다.

## 0. 결론

- 자동입력에 쓸 수 있는 서류는 **32종**입니다. 사용자가 정한 입력 순서(대표자 → 사업자 기본정보 → 사업 현황(과거→현재) → 부채·의무 → 인증 → 계획(미래))에 맞춰 묶었습니다.
- **1차 개발 범위는 8종을 권장합니다.** 홈택스·정부24·등기소에서 무료나 1,000원 이하로 바로 발급되는 PDF 7종(사업자등록증명, 표준재무제표증명, 부가세 과세표준증명, 국세 납세증명서, 지방세 납세증명서, 법인등기 현재사항, 은행 금융거래확인서·부채증명서)과 홈택스 엑셀 1종(전자세금계산서 목록)입니다. 이것만으로 기존 입력칸 약 30개와 대출표 전체를 채울 수 있습니다.
- **추출은 4단계로 나눕니다.** ① 글자가 들어 있는 PDF는 pdf.js로 읽고 ② 엑셀·CSV는 SheetJS로 읽고 ③ 스캔·사진은 브라우저 OCR(tesseract.js)로 읽은 뒤 ④ 모든 경우에 확인표에서 사람이 승인합니다. 클라우드 OCR과 AI 추출은 비용과 개인정보 승인 전까지 보류합니다.
- **원본 파일은 기본적으로 저장하지 않습니다.** 주민등록번호는 읽는 즉시 생년월일만 남기고 버립니다.
- **가장 큰 미확정 사항은 실제 발급본입니다.** 실제로 찍히는 라벨, PDF 안에 글자가 들어 있는지, 은행마다 다른 양식은 웹 자료로 일부만 확인했습니다. 그래서 비식별 샘플 수집을 0번 작업으로 둡니다.

**확인 수준 표기**
- ● 공식 안내나 여러 출처로 확인
- ◐ 실무 지식, 웹으로 일부만 확인
- ○ 실제 샘플로 확정 필요

## 2. 문서별 필드 매칭

- 표기: `기존id` = 지금 앱에 있는 입력칸, `new:` = 새로 제안하는 입력칸. 금액 단위는 문서가 **원**, 앱은 smb·대출표가 **만원**, sme 재무가 **백만원**입니다.
- 라벨은 모두 ◐입니다. 일반 양식 기준이므로 샘플로 정규식을 확정해야 합니다.

## 4. 추출 방식

### 처리 흐름(모든 형식 공통)

1. 드롭존이나 "찾기"로 파일 여러 개를 한꺼번에 받습니다.
2. 형식을 판별합니다(PDF / 이미지 / XLSX·CSV / HWP).
3. 문서 종류를 판별합니다. 제목 키워드(예: "사업자등록증명", "표준재무상태표", "과세표준증명", "납세증명서", "등기사항")와 필수 라벨 2개 이상으로 판정하고, 실패하면 사용자가 드롭다운에서 고릅니다. 한 PDF 안에 여러 서류가 섞이면 쪽마다 판별합니다.
4. 문서 종류별 라벨 사전으로 값을 뽑습니다.
5. 정규화합니다. 금액(쉼표, "△" / "( )" 음수), 날짜(2024년 03월 15일 / 2024.03.15 / 2024-03-15), 단위를 환산합니다.
6. 검증합니다. 사업자·법인번호 검증번호, 대차 일치, D06 매출과 D08 과세표준 합의 차이, **문서의 사업자번호가 현재 고객과 다르면 적용 차단**.
7. 확인표를 띄웁니다.
8. 적용합니다. `applyFormData`는 규모·업종을 초기화하므로 쓰지 않고, 새 함수 `applyFieldPatch(patch, source)`로 칸만 채웁니다.

### 1단계: 글자가 들어 있는 PDF를 브라우저에서 읽기 (pdf.js)

- pdfjs-dist를 **정확한 버전으로 고정**하고, 업로드를 처음 쓸 때만 불러옵니다. 한글 PDF는 **cMap 설정(`cMapUrl`, `cMapPacked: true`)이 없으면 글자가 비거나 깨집니다.**
- `getTextContent()`로 받은 글자 조각을 좌표(y값 허용오차)로 줄 단위로 다시 묶습니다. 라벨 오른쪽이나 바로 아래 칸의 값을 집습니다.
- 라벨은 공백을 지우고 비교합니다. 공문서는 "상 호", "성　　명"처럼 글자 사이를 띄워 둡니다.
- 깨진 글자 비율이 높으면(글꼴에 한글 대응표가 없는 경우) 자동으로 2단계 OCR로 넘깁니다.
- 라벨 사전은 코드 밖 JSON(문서 종류 → 판별 키워드 / 라벨 / 정규식 / 단위 / 대상 필드)으로 둡니다. 양식이 바뀌면 사전만 고칩니다.

### 2단계: 스캔·사진을 OCR로 읽기

| 방식 | 비용 | 장점 | 한계 |
|---|---|---|---|
| **tesseract.js(브라우저)** — 권장 | 무료. 한글 빠른 모델 약 1MB ● | 파일이 PC 밖으로 나가지 않음 | 깨끗한 스캔은 쓸 만하지만 휴대폰 사진·표·손글씨는 약함 ◐. 처음 쓸 때 모델 내려받기 시간. PDF는 pdf.js로 그림으로 그린 뒤 넘겨야 함 ● |
| Google Cloud Vision(문서 글자 인식) | 매월 1,000쪽 무료, 이후 1,000쪽당 $1.50 ● | 정확도 높음 | **국외 이전**. 키를 숨기려면 Supabase Edge Function 필요 |
| 네이버 CLOVA OCR(일반·템플릿) | 호출 건당 과금 ●, 단가는 콘솔에서 확인 필요 ○ | 한국 서류에 강함, 사업자등록증 템플릿 ◐ | 서버 중계 필요, 처리 위탁 고지 |
| AI 비전 추출 | 비용 발생 | 표와 문맥까지 이해 | DEVELOP_PLAN B-5에 따라 **별도 비용 승인 전까지 보류** |

- 권장안: 1차에는 tesseract.js만 씁니다. 대상은 사업자등록증 원본, 임대차계약서, 신용점수 캡처, 인증서입니다. 회색조·이진화·기울기 보정을 거치고, 사람 확인을 필수로 합니다.
- 정답률이 부족하면 그때 CLOVA를 Edge Function으로 붙이는 안을 비용과 개인정보 승인과 함께 따로 결정합니다.

### 3단계: 엑셀·CSV 읽기

- SheetJS를 씁니다. **npm에 남아 있는 `xlsx` 0.18.5는 알려진 취약점(CVE-2023-30533 등)이 있으므로 SheetJS 공식 CDN의 0.20.x를 버전 고정해 씁니다.**
- 제목줄이 섞여 있으므로 머리글 행은 키워드("공급가액", "승인금액")로 찾습니다.
- 확장자는 .xls인데 실제로는 HTML 표인 파일도 SheetJS가 처리합니다.
- CSV는 EUC-KR일 수 있으므로 `TextDecoder('euc-kr')`로 다시 읽어 봅니다.

### 4단계: 사람이 확인하는 화면(모든 경로 필수)

```
┌ 서류 올리기 ─────────────────────────────────────────────┐
│ [여기에 끌어다 놓기 · 찾기]  PDF·사진·엑셀 여러 개 가능 │
│ 파일은 이 PC 브라우저에서만 읽고 저장하지 않습니다       │
├──────────────────────────────────────────────────────────┤
│ ✔ 표준재무제표증명 2024 (발급 10/02)   12개 항목 → [확인]│
│ ✔ 부가세 과세표준증명 2024-2·2025-1     2개 항목 → [확인]│
│ ! 사진: 임대차계약서 (OCR, 정확도 낮음)  5개 → [확인]   │
│ ✖ 다른 회사 사업자번호 → 적용 불가                       │
└──────────────────────────────────────────────────────────┘
확인표:  앱 항목 | 지금 값 | 서류 값 | 출처(쪽·라벨·원문 미리보기) | 신뢰도 | 적용☐
```

- 빈 칸은 "적용"이 미리 체크됩니다. 이미 값이 있는데 서류 값이 다르면 "유지"가 기본이고 차이를 강조합니다(결함 1-9 덮어쓰기 확인 원칙과 같습니다).
- 일괄 적용과 되돌리기를 지원합니다. 적용된 칸에는 출처 배지를 붙입니다.
- 단계마다 "이 단계에 쓰는 서류" 체크리스트를 둡니다. 상태는 미제출 / 추출 완료 / 확인 필요 / 유효기간 만료 4가지입니다.

### 서류끼리 값이 다를 때의 우선순위

- 기본 순서: 국세청·등기소 발급 > 기관 확인서 > 세무대리인 결산서 > 회사 자료 > OCR
- 변동 정보(잔액, 인원, 매출)는 발급일이 더 최근인 서류를 씁니다.
- 불변 정보(번호, 성립일)가 서로 다르면 자동으로 고르지 않고 경고합니다. 다른 회사 서류일 가능성이 있습니다.

## 5. 개인정보와 원본 보관

- **주민등록번호**: 개인정보보호법상 법령 근거 없이 처리할 수 없습니다. 모든 추출 경로 앞에 공통 필터를 둡니다. `\d{6}-?[1-8]\d{6}` 패턴을 찾으면 메모리에서 바로 가리고 생년월일만 계산합니다. `form_data`, 로그, `audit_logs.detail`, 오류 보고 어디에도 남기지 않습니다.
- **명단 서류**(4대보험 명부, 주주명부, 등기 임원): 인원수와 지분처럼 계산 결과만 남깁니다. 대표자가 아닌 사람의 이름은 저장하지 않습니다.
- **계좌번호**(`corp_main_bank`): 은행명과 끝 4자리만 남기기를 권장합니다.
- **신용점수·연체 정보**: 대표자 개인신용정보입니다. 입력 전에 동의 체크와 동의 기록을 남깁니다. 동의 요건은 법률 검토가 필요합니다.
- **원본 파일**: 기본은 **보관하지 않습니다.** 브라우저에서 읽고 바로 버리며 서버로 보내지 않습니다. 보관이 꼭 필요하면 펌 관리자가 켜는 옵션으로 둡니다.
  - Supabase Storage 비공개 저장소 `evidence/{org_id}/{assessment_id}/`, 같은 펌만 접근(RLS)
  - 보관기간을 강제하고 자동 삭제(예: 진단 확정 후 90일)
  - 업로드·열람·삭제를 `audit_logs`에 기록, 파일명에 개인 이름을 넣지 않음
  - 무료 용량이 1GB이므로 용량 관리 필요
  - 별도 테이블 `evidence_files`가 필요해 마이그레이션을 새로 만들어야 함
- **클라우드 OCR을 켜면** 처리 위탁(구글이면 국외 이전) 고지와 동의가 필요합니다. 그림 속 주민번호를 미리 가리기 어려우므로 등기와 개인사업자 서류는 클라우드로 보내지 않습니다.
- **로그**: "추출" 행위는 문서 종류와 항목 수만 기록하고 값은 기록하지 않습니다.

## 6. 위험과 대응

| 위험 | 영향 | 대응 |
|---|---|---|
| 실제 발급본의 라벨과 글자 포함 여부 미확정(웹으로는 일부만 확인) | 정규식이 처음부터 맞지 않음 | U0에서 비식별 샘플을 서류별로 2~3건(개인·법인) 모아 기대값 JSON으로 고정 |
| 홈택스·은행 양식 변경 | 파서가 조용히 틀린 값을 냄 | 라벨 사전을 외부 JSON으로, 필수 라벨이 없으면 "판별 실패"로 수동 처리, 시나리오 테스트에 포함 |
| PDF에 글자가 없거나 복사 방지, 가상 프린터 차단 ● | 1단계 실패 | OCR로 자동 전환. "PDF 발급" 메뉴로 받으라고 안내 |
| 금액 단위 착오(원 / 천원 / 백만원) | 1,000배 오류 | "단위" 문구 탐지 + D06·D08 교차 검산 + 앱 단위 변환표 하나로 관리 |
| 연도 열 착오(당기·전기, 3월 결산, 기존 id의 고정 연도) | 재무 추이가 뒤바뀜 | `sme_fy_y1`을 도입하고 확인표에 연도를 크게 표시 |
| 음수 표기(△ / 괄호) 누락 | 적자가 흑자로 둔갑 | 정규화 규칙 + 시나리오 테스트 |
| 등기 말소사항이 섞임 | 옛 상호·주소·대표 | 현재사항증명서 권장, 가장 최근 등기일 우선 |
| 다른 회사 서류 혼입 | 고객 정보 오염 | 사업자·법인번호가 다르면 적용 차단 |
| 크레딧포유에 금리 없음, 은행 양식 제각각 | 대출표 불완전 | 크레딧포유 행을 초안으로 만들고 은행 서류로 금리·만기 보완 표시 |
| OCR 정확도(사진, 손글씨 임대차계약서) | 잘못된 금액 | 신뢰도 표시 + 사람 확인 필수, 자동 적용 금지 |
| 개인정보가 로그·클라우드로 새어 나감 | 법적 위험 | 공통 마스킹 필터, 클라우드 OCR 기본 끔, 로그에 값 저장 금지 |
| 외부 CDN 의존(pdf.js·tesseract·SheetJS) | 첫 로딩 지연, 오프라인 원칙 약화 | 정확한 버전 고정 + 업로드할 때만 불러오기. 오프라인이면 "수동 입력" 안내 |
| 모델이 추출값을 사실로 오인 | 고객 문서 오류 | 추출값은 "서류 기재값"일 뿐 원본 진위는 발급번호로 따로 확인한다고 표시. 서류는 가공하지 않고 읽기만 함 |

## 7. 개발 묶음(업로드 자동입력 트랙)

| 묶음 | 내용 | 완료 기준 |
|---|---|---|
| **U0** 샘플·라벨 사전 | P1 서류 8종의 비식별 샘플 수집, `doc_registry.json`(판별 키워드·라벨·정규식·단위·대상 필드), 서류별 기대값 JSON | 서류마다 샘플 2건 이상 + 기대값 확정, 글자 포함 여부 판정표 |
| **U1** 업로드 틀 | 전체 드롭존 + 단계별 서류 체크리스트, 여러 파일, 형식·문서 종류 판별(실패 시 수동 지정), 파일은 메모리에서만 처리 | 32종 목록이 화면에 나오고, 판별 결과와 실패 시 수동 지정이 동작 |
| **U2** PDF 읽기 + P1 서류 | pdf.js + cMap, 좌표 기준 줄 재구성, 라벨 앵커. D01·D03·D06·D08·D22·D23 | 샘플 기대값과 일치율 표 기록(목표 필드 95% 이상) |
| **U3** 확인표·적용 | `applyFieldPatch`, 출처 배지(`form_data.sources`), 덮어쓰기 규칙, 되돌리기, 교차 검산, 다른 회사 차단 | 기존 값 보존 시나리오와 다른 회사 서류 차단 시나리오 PASS |
| **U4** 엑셀 | SheetJS 0.20.x(공식 CDN), D11 매출처·매입처 상위 5곳과 비중, D12 월평균 | 실제 파일 2건에서 상위 거래처와 비중 일치 |
| **U5** 부채 서류 | D17 은행별 라벨 사전(주요 5개 은행부터), D18 초안, 대출표 새 열, 이자·고금리·보증 판정 | 대출 3건 샘플의 합계·가중평균금리 재계산 일치 |
| **U6** 인증·규모·인력 | D05·D14·D15·D25~D30, `certItems`·`ipItems`, 미래 일정(만기·만료) 목록 | 유효기간이 지나면 "만료" 표시, 서식3 일정 반영 |
| **U7** OCR | tesseract.js 필요 시 불러오기, 전처리, D02·D16·D20·D31 | 신뢰도 표시, 자동 적용 0건(모두 확인 거침) |
| **U8** 개인정보 장치 | 주민번호 공통 필터, 동의 체크, 원본 미보관 기본값, (선택) Storage 보관·만료·감사 로그 | 모든 샘플 처리 후 저장 데이터·로그에서 주민번호 패턴 0건 |
| **U9** 검증 | `tools/scenarios`에 "업로드 → 추출 → 기대값 대조" 추가, 결과를 `tests/결과_*.md`에 기록 | `check.js` + 시나리오 전체 PASS, 정답률 표 |

**권장 순서**: U0 → U1 → U2 → U3 (여기까지가 1차 출시) → U5 → U4 → U6 → U8 → U7. U8의 주민번호 필터는 U2와 함께 먼저 넣습니다.

**샘플 요청(사용자에게 받을 것, 개인정보 가린 실제 발급본)**
- 필수: 사업자등록증명(개인·법인), 표준재무제표증명 3개 연도, 부가세 과세표준증명, 국세·지방세 납세증명서, 법인등기 현재사항
- 은행: 주요 은행 금융거래확인서와 부채증명서 각 1건
- 엑셀: 홈택스 전자세금계산서 매출·매입 엑셀
- 기타: 4대보험 가입자명부, 벤처확인서
